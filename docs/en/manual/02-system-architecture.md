# System Architecture

The project is composed of two main elements: **the AGV robot with manipulator** and **the XR application on Meta Quest**. The application in the headset allows operating the robot, visualizing sensor information, and deciding which data should be sent from the robot to avoid transmitting unnecessary information.

In general terms, the architecture works as follows:

![Architecture]({{ "/assets/img/Diagrama general.png" | relative_url }})


The central idea of the system is that the **NUC (the robot's brain) acts as coordinator**, while other subsystems execute low-level tasks such as motor control, PWM, ramps, driver signals, and calibration routines. This allows commands sent from the XR interface to be simple, with the complexity of movement resolved within the robot.

## XR interface on Meta Quest

The user interface runs on the Meta Quest headset via an application developed in Unity. From this interface the operator can see the robot's status and send operation commands.

The main elements of the interface are:

| Element | Function |
|---|---|
| Video panel | Shows the streaming from the robot's camera. |
| LiDAR panel | Visualizes spatial information generated by the RPLiDAR. |
| Mode buttons | Allow requesting which type of information the robot should send. |
| Movement controls | Send velocity commands. |
| Manipulator controls | Send angle references for the arm's axes. |

The Meta Quest does not receive all data at all times. The operator can request different transmission modes. For example, in the case of LiDAR, the interface can request information in **panorama**, **medium**, or **detailed** mode. This way, the robot sends only the resolution necessary for the current task.

It is also possible to enable or cancel the video streaming from the XR interface. This helps reduce network load when the operator does not need to visualize the camera in real time.

## ZMQ communication

The main communication between the Meta Quest and the NUC is carried out via **ZMQ** over WiFi. The system separates the types of information into distinct channels to keep the data flow organized.

| Channel | Direction | Content |
|---|---|---|
| Video | NUC → Meta Quest | Compressed camera frames for XR visualization. |
| Sensors / status | NUC → Meta Quest | LiDAR information, system status, mode confirmations, and telemetry. |
| Commands | Meta Quest → NUC | Orders for movement, manipulator, video, and sensor modes. |

This separation allows video, sensors, and commands to not depend on a single flow. Thus, if video is reduced or disabled, control commands and status information can keep working.

## Onboard NUC

The Intel i7 NUC is the robot's main computer. Its function is to receive commands from the Meta Quest, coordinate the sensors, and communicate with the embedded electronics.

The NUC is connected via USB to:

- **RPLiDAR C1**, used to obtain 2D information about the environment.
- **Intel RealSense camera**, used for video and RGB-D perception.
- **Master H-bridge module**, in charge of connecting the computer with the network of embedded boards.
- **Gripper ESP32-C3**, connected directly to the NUC via an independent serial channel (USB) for control and status reading of the gripper.

The NUC does not directly control all electrical details of the robot. Instead, it sends simpler instructions to the ESP32-C3 modules. For example, it can indicate a desired velocity or a target angle, while the boards handle translating that into specific electrical signals.

## Robot embedded network

The robot has four boards designed for this project:

1. **Master H-bridge**
   Receives commands from the NUC via USB and controls one of the traction motors. It also coordinates I2C communication with the other boards.

2. **Slave H-bridge**
   Communicates with the master via I2C and controls the second traction motor. Executes local tasks such as PWM and acceleration ramps.

3. **NEMA 17 driver controller**
   Controls three external manipulator drivers via **PUL**, **DIR**, and **ENABLE** signals. Also integrates digital inputs intended for limit switches and calibration routines.

4. **Gripper ESP32-C3**
   Board dedicated to the gripper, connected directly to the NUC via USB (a serial channel independent from the master's). Reports real-time status (position in mm, busy, calibrated) and receives position commands from the NUC.

The H-bridge has a physical DIP switch selector that allows configuring different operating modes. These include modes such as master, slave 1, slave 2, and slave 3. In addition, the board was designed to support different forms of communication, such as USB/UART, I2C, Bluetooth, external Bluetooth module, and WiFi.

In the current configuration, the master module is connected to the NUC and the other boards work as slaves within the I2C bus.

## Manipulator control

The manipulator uses three NEMA 17 motors controlled by external drivers. The board dedicated to the manipulator generates the necessary signals for each axis and allows movements to be executed in a more structured way.

The system includes limit switches to support calibration processes. The board also includes a physical test button that can execute a zero-search routine. Once the manipulator is calibrated, movements are performed within the maximum ranges defined for each joint.

This means that from the Meta Quest it is not necessary to send individual pulses or low-level logic. The interface only sends movement references, and the robot's electronics handle executing the action in a controlled manner.

## Operation flow

A typical operation cycle occurs as follows:

1. The operator uses the Meta Quest to activate video, select LiDAR resolution, or move the robot.
2. The XR application sends a ZMQ command to the NUC.
3. The NUC interprets the command and decides whether to change a sensor mode, stream video, or send an order to the embedded boards.
4. If the command involves movement, the NUC sends it to the master module.
5. The master executes its part of the control and, if necessary, distributes instructions via I2C to the slave H-bridge or the manipulator controller.
6. The sensors capture information about the environment and the NUC sends back to the Meta Quest only the requested data.

## Design criteria

The architecture seeks to divide responsibilities clearly:

- **Meta Quest:** operation, visualization, and mode selection.
- **NUC:** general coordination, sensors, streaming, and ZMQ communication.
- **ESP32-C3:** low-level embedded control.
- **Designed boards:** electrical adaptation, motor control, and driver signals.
- **Sensors:** environment perception via LiDAR and RGB-D camera.

This division makes the system more modular. The XR interface can remain simple, the NUC can focus on communication and perception, and the embedded boards can resolve electrical and mechanical control locally.
