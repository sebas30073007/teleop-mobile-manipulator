Necesito reestructurar la herramienta de pruebas de latencia WF-IoT MR–Edge para que las pruebas sean iniciadas y controladas desde la PC, no desde la interfaz de Quest.

Contexto:
Ya existe una planeación para crear archivos nuevos bajo validation/ y docs/, sin modificar scripts existentes del proyecto principal. La interfaz Unity ya se ve en escena, pero actualmente no es práctico hacer clic desde Meta Quest. Por eso quiero que la PC, que simula la NUC/edge node, sea quien orqueste las pruebas. Meta Quest debe comportarse como endpoint automático: se conecta a la PC, recibe streams simulados y responde probes de latencia.

Objetivo nuevo:
Convertir la herramienta en un sistema PC-driven:

PC simulando NUC:
- inicia cada condición experimental C1–C7,
- activa/desactiva video sintético,
- activa/desactiva LiDAR sintético,
- publica carga de sensores/video,
- envía probes de latencia hacia Quest,
- recibe respuestas de Quest,
- calcula RTT usando solo el reloj de la PC,
- guarda CSV detallado y CSV resumen.

Meta Quest / Unity:
- se conecta automáticamente a la IP de la PC configurada en Inspector,
- no requiere interacción manual con botones,
- recibe video/sensores para generar carga realista,
- escucha probes enviados por la PC,
- responde inmediatamente a cada probe,
- opcionalmente muestra métricas en pantalla, pero no es quien controla la prueba.

Importante:
- No modificar scripts existentes del proyecto principal.
- No modificar MainScene.
- Trabajar solo en archivos nuevos dentro de validation/ y Assets/Scripts/WFIoTLatency/ si ya fueron copiados al proyecto Unity.
- Mantener un socket ZeroMQ por thread.
- La medición sigue siendo latencia MR–edge/protocolo, no latencia física completa del robot.

============================================================
CAMBIO DE ARQUITECTURA DE MEDICIÓN
============================================================

Antes:
Unity enviaba latency_probe por 5002 y Python respondía latency_ack por 5001. Unity calculaba RTT y guardaba CSV.

Ahora:
Python/PC envía pc_latency_probe por 5001.
Quest responde latency_pong por 5002.
Python/PC calcula RTT y guarda CSV.

Flujo deseado:

PC Python
  PUB :5001 topic pc_latency_probe
      ↓
Quest Unity endpoint
  recibe probe
  responde por PUB :5002 topic cmd, type latency_pong
      ↓
PC Python
  SUB :5002 recibe pong
  RTT = pc_receive_time - pc_send_time

Ventaja:
- No se necesita tocar la UI del Quest.
- No hay que extraer CSV del Quest.
- No se usan relojes diferentes para RTT.
- La PC guarda todos los resultados.

- No depender de timestamps de Quest para calcular RTT.
- Guardar quest_recv_unity_time y quest_send_unity_time solo como información adicional.

UNITY — QUEST ENDPOINT AUTOMÁTICO
============================================================

Crear nuevos scripts si no existen o modificar solo los nuevos bajo WFIoTLatency.

Agregar un script nuevo recomendado:
WFIoTQuestEndpointResponder.cs

Responsabilidad:
- Conectarse automáticamente a la PC.
- Suscribirse al puerto 5001 a:
  - pc_latency_probe
  - test_control
  - stat
  - lidar_grid opcional si se quiere contar carga
- Publicar respuestas por 5002 topic cmd:
  - endpoint_ready
  - latency_pong
  - endpoint_status

El script debe funcionar sin UI.

Campos públicos en Inspector:
string pcIp = "192.168.1.100";
bool autoConnectOnStart = true;
int sensorPort = 5001;
int commandPort = 5002;
bool respondToProbes = true;
bool sendEndpointReady = true;

Al iniciar:
1. AsyncIO.ForceDotNet.Force().
2. Crear thread endpointThread.
3. En endpointThread:
   - SUB connect tcp://<pcIp>:5001
   - Subscribe("pc_latency_probe")
   - Subscribe("test_control")
   - opcional Subscribe("stat"), Subscribe("lidar_grid")
   - PUB connect tcp://<pcIp>:5002
4. Enviar endpoint_ready por topic cmd:
{
  "type": "endpoint_ready",
  "device": "MetaQuest",
  "unity_time": <Time.realtimeSinceStartup capturado de forma segura o 0 si está en thread>,
  "notes": "Quest endpoint connected"
}

Como Time.realtimeSinceStartup no debe llamarse desde thread secundario, si se necesita unity_time preciso:
- Capturarlo en main thread y compartirlo con lock; o
- En endpoint_ready usar 0 y no depender de ese valor.

Al recibir pc_latency_probe:
- Responder inmediatamente por PUB :5002, topic cmd:
{
  "type": "latency_pong",
  "seq": <seq recibido>,
  "pc_send_unix": <pc_send_unix recibido>,
  "quest_recv_unity_time": <opcional>,
  "quest_send_unity_time": <opcional>,
  "test_id": "<test_id recibido>",
  "condition": "<condition recibido>"
}

Prioridad:
- Respuesta inmediata desde el thread de red.
- No depender del hilo principal para responder.
- Si no se puede usar tiempo Unity en thread, mandar quest_recv_unity_time=0 y quest_send_unity_time=0.
- El RTT oficial lo calcula Python con su propio reloj.

Al recibir test_control:
- Actualizar variables internas:
  - currentTestId
  - currentCondition
  - cameraMode
  - lidarMode
  - videoEnabled
  - lidarEnabled
- Opcional: mostrarlo en UI si existe.
- No iniciar nada desde Quest; solo responder y consumir streams.

Video y sensores:
Mantener o crear receivers nuevos que se conecten automáticamente:
- WFIoTSimVideoReceiver:
  - SUB 5555 video_rgb
  - contar frames y bytes
  - no decodificar por default
- WFIoTSimSensorReceiver:
  - SUB 5001 stat/lidar_grid
  - contar mensajes y bytes
  - no renderizar

Estos receivers sirven para que Quest realmente reciba carga de video y LiDAR durante C2–C7.

UI:
La UI actual puede quedarse como monitor, pero ya no debe ser necesaria.
Agregar en pantalla:
- endpoint status,
- current condition,
- probes received,
- pongs sent,
- video FPS received,
- lidar Hz received.

Pero no se requiere que botones funcionen para correr la prueba.
